# FracVibe — decision ledger (append-only)

One row per decision. **Append-only**: a decision is history and history never
rots, so never edit another landing's row. Each row names its provenance and what
was rejected. Where the owner's words are on file they are quoted; where they are
not, the row says so rather than inventing an authority.

| 6 | **The objective is "resilient and correct", and the METHOD is the dispatcher's judgement, executed as a sequenced campaign.** The bar is defined as CORRECT (every renderer agrees with one mathematical definition at every reachable control setting) and RESILIENT (no single failure leaves a blank canvas, a wedged UI, or an uncaught exception), each behaviour PINNED by a test shown red on a deliberately broken build. | Owner's verbatim words, 2026-09-21: *"I want this to be resilient and correct, you can take your time to achieve that state. | 7 | **S1: the zoom clamp lives in `FractalViewer` alone (`setZoomLimit`/`clampScale`), and the cap is applied to the STORED view, not to a copy the animation can overwrite.** `setView`, `onWheel`, the startup animation and `renderWebGL` all read the one clamp, so the three pre-S1 paths cannot disagree; both `setView` monkey-patches, the render-time clamp and the dead wheel guard are deleted. | The probe found the cap written three ways (`app.js:221-241`, `601-623`, `651-665`) with the only correct copy re-installed per GPU entry, and `fractalViewer.js:116-121` unreachable because `WEBGL_MIN_SCALE`/`webglCheckbox` are `app.js` module-locals. The animation mutated `viewer.view.scale` directly, so even a correct patch would have been overwritten on the next frame. Pinned, all three paths to the same value, by `tests/zoom-clamp.spec.js`. | Keeping the `viewer.setView` patch and fixing only its re-installation; clamping at render time instead of at view-set time (that leaves `viewer.view` itself lying about the scale it will draw). | Writer, `session-s1-canvas`, 2026-09-21, from the brief's item 4 and the probe's "one clamp, not three". |
| 8 | **S1: a lost or released WebGL context replaces the `<canvas>` element; renderer teardown is idempotent and accounts for itself.** `destroy()` deletes the program, both shaders and the quad buffer, then releases the context via `WEBGL_lose_context`; `window.__fvLiveWebglRenderers` (from the renderer itself) is the observable the suite asserts. | A canvas whose context has been created and then lost never returns a new context from `getContext`, so a GPU→CPU→GPU toggle would silently degrade to CPU forever. The old `destroy()` only nulled `gl`, leaking a program, two shaders, a buffer and a context per toggle. The suite may not INFER the leak from pixels, so the renderer exposes a construction/destruction counter and the pin asserts 0 after each teardown. Pinned by `tests/webgl-fallback.spec.js` (5 toggles, plus a simulated context loss). | Asserting "one context" by counting `getContext` calls or by pixel-diffing (both are inference, not observation); `preventDefault()` alone with no element swap (restoration is async and never arrives in practice). | Writer, `session-s1-canvas`, 2026-09-21, from the brief's item 3 and the "make it observable" pin. |
| 9 | **S1: `window.confirm` at the GPU zoom cap is KEPT (deferred by 10 ms), but every other WebGL failure reports through a new non-modal `#appMessage` element.** The one-shot switch-to-CPU offer stays a modal because the brief scoped only `alert`; it is recorded here as a smell. | The B9 finding was that `alert` + `viewer.render()` left a blank canvas with no CPU calculation; the container's decision (`docs/PLAN.md` S1) was "fall back to the CPU worker path and report through the existing info/status UI rather than `alert`". Moving the zoom-cap offer off `confirm` is a behaviour change S1 does not need, and `deniedCpuSwitchAtZoomCap` already makes the prompt once-only. | Silently dropping the offer (removes a user-visible capability), and keeping the three modal sites while adding a separate non-modal one (the duplication item 4 exists to remove). | Writer, `session-s1-canvas`, 2026-09-21. Flagged for the dispatcher: if the owner wants no modals at all, that is a one-row change in `handleZoomLimitReached`. |
| 10 | **S2: cancellation is `worker.terminate()` + respawn, not job slicing.** `cancelJob()` counts a real cancellation (`cancelledWorkers`), terminates the live worker and constructs a fresh one; every view change routes through it, and `startFractalCalculation` also cancels a superseding job. | A worker inside its synchronous kernel cannot receive `postMessage({type:'abort'})`, so the pre-S2 abort was a no-op (the probe's B6); and a *sliced* worker that yields between chunks is only cancellable at a yield point — it needs message handling and re-entrancy in the kernel, and a cancel still waits for the current slice. Terminate is immediate, unconditional and leaves nothing to reuse. `workerGeneration` (spawns) and `cancelledWorkers` (kills) make both halves countable; the pin asserts the kill counter rises on a cancel during a long job, and an inert `cancelJob` makes it go red. | Slicing + yielding (more kernel surface, cancellable only at yield points); keeping the `abort` post and relying on the `calcToken` alone (that is exactly the pre-S2 no-op). | Writer, `session-s2-worker`, 2026-09-21, from the brief's item 1 and the probe's flow-3 row. |
| 11 | **S2: progressive refinement is APPLIED, not deleted.** The worker refines one buffer 8 → 4 → 2 → 1 and posts a frame for **every** level (earlier levels copy the buffer, the final one transfers it); `app.js` applies `progress` frames exactly as it applies `done`. | The halving existed precisely so a coarse image could appear early, but `app.js` handled only `'done'`, so all three intermediate frames were computed and thrown away — the latency work was paid and the benefit discarded. Applying them makes a slow render converge instead of staying stale until the last pixel, which is the resilience the campaign's bar names. It is *observable*: `appliedFramesForJob(jobId) > 1` (one frame can be final, every further one is intermediate) and `progressFrames()` are counted, so the pin goes red when no non-final frame is posted. | Deleting the halving and going straight to `gridStep 1` (simpler, and it drops the redundant per-level copy, but it throws away the only progressive feedback the app has — a slow render then shows nothing until it is finished). | Writer, `session-s2-worker`, 2026-09-21, from the brief's item 3. |
| 12 | **S2: `worker.onerror` surfaces a message and retires the worker.** It reports through the existing non-modal `#appMessage` (S1) with the worker's message, drops the in-flight job, and `terminate()`s the failed worker so the next job gets a clean one. | Pre-S2 there was no `onerror` at all, so a worker failure was completely silent: the canvas kept its last frame and nothing was reported. The S1 window error net is not a substitute — a worker script error reaches the page as an `ErrorEvent` on the worker, and the pin asserts a sentinel that only the worker handler produces, plus the worker count going to zero (which the window net cannot do). | Auto-restarting the failed job (an unbounded retry loop on a worker that always fails); leaving the worker in place (the next job would post to a worker whose script may not have loaded). | Writer, `session-s2-worker`, 2026-09-21, from the brief's item 2 and the probe's failure-path row. |
| 13 | **S2: a malformed frame is validated before it becomes pixels, and the `calcToken`/generation checks are DEFENCE IN DEPTH, not the net.** `applyWorkerFrame` rejects a payload that is not a whole-`Int32Array` or whose length is not exactly `width × height`, reports through `#appMessage` and ends the job; the net that actually stops a late frame from a cancelled job is clearing `progressiveState` on cancel. | The probe called the bad-payload path an uncaught `Int32Array(undefined)`; measured on V8 that constructor does **not** throw (it yields an empty array), so the real defect was a *silently wrong* frame (an empty or short buffer passes `FractalViewer.render`'s length guard and paints the background). The guards were measured, not assumed: with both `calcToken` and generation checks deleted the cancel pin still passed, so the state clear is what protects; the checks stay because they also catch a frame that raced in before `terminate()` took effect, and removing them is not worth the risk. `terminate()` itself was measured to be **asynchronous with respect to a synchronous kernel** — the level already running still finishes (CPU 1.04 s with terminate vs 1.02 s without) — so "cancel stops the CPU immediately" is NOT claimed and is not pinned. | Inferring a leak from pixels; asserting the cancel stop by CPU time (it does not distinguish, measured); shipping without the length check and calling an empty buffer "handled". | Writer, `session-s2-worker`, 2026-09-21, from the brief's item 4 and the writer's own control runs. |
| 14 | **S3: Option A — ONE kernel file with no `import` and no `export`, publishing `globalThis.FractalKernel`, so the classic worker (`importScripts`) and the ES-module main thread load the same source.** `public/fractalEngine.js` and `public/fractalEngineMain.js` are deleted; the worker's inline override is deleted; `fractalWorker.js` only calls `self.FractalKernel.calcFractalChunk`, and `app.js` / `fractalViewer.js` / `webglFractal.js` / `colorSchemes.js` load the kernel with a side-effect `import`. | The worker is CLASSIC — `app.js` does `new Worker('fractalWorker.js')` and `fractalWorker.js:1` does `importScripts(...)` — while the main thread is ES-modules-only. A file with no import/export statements is simultaneously a valid classic script and a valid ES module, so one source serves both with **no build step and no change to worker loading**; the compile tier parses the file as both `.cjs` and `.mjs`, and the 25-test suite renders through both loaders (pins 1–3). | **Option B** (`new Worker(url, { type: 'module' })` + a normal ESM kernel). Cleaner in the abstract, but it changes worker loading and still cannot serve the classic path; Option A proved adequate in the browser, so B was not taken. Also rejected: keeping a copy of the kernel for the worker (the pre-S3 duplication itself). | Writer, `session-s3-kernel`, 2026-09-21, from the brief's "Design decision". |
| 15 | **S3: the ONE iteration cap is `MAX_ITER = 2000` in `public/fractalKernel.js`.** The slider's `max`, the kernel's clamps (worker chunk and 3D heightmap), the fragment shader's loop bound and the `u_maxIter` uniform clamp all derive from it: `index.html`'s hardcoded `max="2000"` is deleted (app.js sets the attribute from the constant) and the four `for (int i = 0; i < 1024; i++)` literals become `i < MAX_ITER`, templated in by `webglFractal.js` as `#define MAX_ITER <cap>` from the kernel. | B5: `index.html:33` offered up to 2000 while the shader looped to a hardcoded 1024, so every pixel needing >1024 iterations was coloured as escaped (GPU and CPU silently disagreed). GLSL ES 1.00 requires a **constant expression** as a loop bound, so a uniform cannot bound the loop — the source must be generated. 2000 (not 1024) preserves the iteration depth the UI already advertised and the CPU always honoured. | Lowering the cap to 1024 (an equally valid fix, but it deletes CPU capability the app already had); a uniform loop bound (illegal in GLSL ES 1.00); clamping per renderer only (leaves the UI advertising more than the GPU honours — the exact B5 symptom); pinning `cap > 1024` in the suite (it would freeze this slice's choice and fail the alternative fix). | Writer, `session-s3-kernel`, 2026-09-21, from the brief's "one constant" mandate and the measured control arms. |
| 16 | **S3: ONE type/palette table, in the kernel.** `FRACTAL_TYPES` and `COLOR_SCHEMES` (value, label, shader index, GLSL identifier, palette fn) are the only such lists: app.js populates both `<select>`s from them, the GPU type/palette indices come from `indexForType`/`indexForColorScheme`, the 2D LUT and the 3D heightmap palette come from the same table, and `webglFractal.js` templates `#define FT_*` / `#define CS_*` from it so a GLSL branch cannot drift from the map. The palette implementations move into the kernel; `public/colorSchemes.js` becomes a two-line ES-module re-export for its existing importers. | The audit's "type/palette index maps are duplicated too": `app.js`'s `typeMap` and `colorSchemeMap`, the shader's integer `== 1/2/3` branches, and the `<option>` lists in `index.html` were four to five restatements of the same two ordered lists — exactly the kind that drifts silently when a type or palette is added. Pinned per type and palette by `tests/kernel-parity.spec.js` pin 3. | Leaving the `<option>` markup and the two app.js maps as constants and unifying only the iteration math; keeping the palette functions in `colorSchemes.js` while the kernel holds only the index table (two tables whose ORDER must agree, which is the drift this row removes). | Writer, `session-s3-kernel`, 2026-09-21. |
| 17 | **S3 pins: compare CPU and GPU through a sampled grid with stated thresholds, and observe the shader template rather than infer it.** Pin 1 renders at maxIter = the cap in a deliberately interior-heavy view and requires mean per-channel \|CPU−GPU\| < 6 and >48-off fraction < 0.06 (measured correct 0.911 / 0.0105; with the four loop bounds hardcoded to 1024 the mean \|Δ\| is 82.56, i.e. >13× the threshold). Pin 2 reads the slider's `max`, `__fv.maxIterCap`, the value templated into `#define MAX_ITER` and the bound token of all four loop sites (`['MAX_ITER', …]`, length 4). Pin 3 samples 32×32 pixels per type and palette and asserts inside/outside disagreement < 0.06 and mean \|Δ\| < 20 (correct worst 0.011 / 8.1; a drifted type index gives 0.111; a drifted palette index gives 0.81–0.89 xor or \|Δ\| 39.5–97.0). | The residual CPU/GPU difference is real and is not a defect: the CPU kernel samples pixel **corners** while a fragment shader samples fragment **centers**, so a thin band along the set boundary flips. An exact-equality pin would be red on every correct build; stating the measured residual and the margin makes the pin honest. The shader's bound is an artifact, so it is READ from the generated source (the four loop tokens + the `#define` value exposed on the renderer) instead of inferred from pixels — a `#define` of 4096 with the uniform still clamped to 2000 renders identically to correct code, yet pin 2 must (and does) go red on it. | Pixel-exact equality; screenshot/eyeball agreement; inferring the shader bound from pixels; a single "looks similar" threshold without separating type drift (shape) from palette drift (colour). | Writer, `session-s3-kernel`, 2026-09-21; thresholds and all five control arms recorded in the landing report. |
